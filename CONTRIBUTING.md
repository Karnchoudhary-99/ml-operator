# Contributing to ml-operator

Thanks for picking this up. The short version: small, complete
changes, on a branch, with tests, merged — never squashed.

## Workflow

1. Branch from `main`: `feat/<topic>`, `fix/<topic>`, `docs/<topic>`.
2. Commit after every logical unit, with a conventional message:
   `feat: …`, `fix: …`, `docs: …`, `test: …`, `refactor: …`,
   `chore: …`. No empty, trivial, or drive-by commits.
3. Push the branch, open a PR, merge with a **merge commit**
   (not squash). Keep the history readable — it is part of the
   review.
4. One PR, one coherent change. If the change grows a second
   purpose, split it.

## Before you push

Run what CI runs, in this order:

```bash
test -z "$(gofmt -l .)"   # gofmt -l exits 0 even when it lists files: gate on empty output
go vet ./...
go test ./...
go build ./...
for t in examples/*-tour.sh; do bash "$t"; done
```

The full test suite takes ~15 seconds locally. If a local step
cannot run on your machine (a missing shell, a localhost quirk),
say so in the PR — GitHub Actions is the verification of record,
and a skipped local step is never a reason to push untested code.

## Adding a command to `mlop`

A new command touches four places; miss one and the suite or a
tour will tell you:

1. `cmd/mlop/<name>.go` — the command, using the same pattern as
   its neighbours: a `flag.FlagSet` with `ContinueOnError`, a
   `Usage` line, `reorderFlags` so flags may follow the name, and
   exit `2` for usage errors, `1` for runtime failures.
2. `cmd/mlop/main.go` — the dispatch `switch` and the `usage`
   text.
3. `internal/completion/completion.go` — the command table, so
   bash/zsh/fish all complete the new command, its flags, and its
   deployment name. The table is the single source of truth: the
   shared test fails if any command or flag is missing from any
   generated script.
4. Tests in `cmd/mlop/` (`runCLI` / `runCLIState` helpers in
   `main_test.go`) and, for a user-visible flow, a tour in
   `examples/`.

## Adding a tour

Tours live in `examples/*-tour.sh` and run in CI on every push
and PR. Use `examples/tour-lib.sh`: `expect` runs a command,
captures its whole output, and only then checks it — never pipe
mlop straight into `grep -q`, because grep exits on the match
while mlop still writes, and under `set -o pipefail` that SIGPIPE
kills the tour. A failed assertion prints the full captured
output, so write tours that say what mlop actually did.

## Generated files

Some outputs are generated and golden-tested — never hand-edit
them:

- `examples/crd.yaml`, `examples/install.yaml` — from
  `mlop crd` / `mlop install`. Regenerate after any schema or
  install change.
- The shell completion scripts — from `mlop completion
  <bash|zsh|fish>`, generated by `internal/completion`.

## Docs

If a change alters behaviour, update the docs with it in the same
PR: the README section for the feature, `docs/operations.md`
for runbook material, `docs/architecture.md` for design, and the
roadmap checkbox in the README. Docs that drift from the code are
worse than no docs.

## What "done" means

Working code, tests alongside it, README/docs updated, no
TODO/FIXME stubs left behind, no secrets or credentials anywhere
in the tree. If a test catches a bug, fix the code (or the test,
when the expectation was the wrong one) — and say which in the
commit message.
